Contexte & Objectifs

Présentation du besoin métier et du cadre du projet

Contexte métier

Le Pôle R&D Semences d'une grande entreprise de distribution semencière réunit plus de 300 spécialistes (sélectionneurs, bioinformaticiens, agronomes). Ce pôle conduit chaque année des centaines d'essais culturaux sur le territoire français pour évaluer la performance des lignées génétiques en conditions réelles.

Ces essais génèrent des données hétérogènes et volumineuses : rendements agronomiques, conditions culturales (sols, météo), données génomiques, coordonnées GPS, qualifications d'experts… dispersées dans de multiples systèmes sources.

Problème identifié : Les données sont cloisonnées, les analyses sont manuelles et longues. Il n'existe pas de vision consolidée permettant de comparer les performances génétiques inter-régions, inter-années et inter-espèces en temps quasi-réel.

Objectifs du projet

  • 🎯 Consolider toutes les sources de données dans un lac de données unique (Data Lake HDFS)
  • 🔄 Automatiser les flux d'ingestion et de transformation (NiFi, Sqoop, Talend)
  • 📊 Analyser les performances par espèce, région, trait et lignée génétique
  • ⚡ Streamer les nouveaux résultats d'essais en temps réel (Kafka)
  • 🗄️ Stocker en NoSQL pour les accès rapides par clé (HBase)
  • 📈 Visualiser via des dashboards interactifs (Tableau / Spotfire style)

Pipeline — 12 Phases Détaillées

Description fonctionnelle de chaque étape

Phase 01 — Apache Sqoop (Ingestion) ✔ 5.5s — 326 688 lignes

Sqoop simule l'import des 6 CSV sources vers HDFS en Parquet/Snappy. Chaque import est configuré avec --num-mappers 4 (parallélisation), --as-parquetfile et --compress. Les jobs sont loggés avec horodatage et métadonnées dans reports/sqoop_jobs.json.

sqoop import --connect jdbc:mysql://crisp-db:3306/semences \
  --table RESULTAT_ESSAIS --as-parquetfile --compress \
  --num-mappers 4 --target-dir /user/semences/raw/resultats
Phase 03 — Apache NiFi (Orchestration) ✔ 10.7s — 6 flows

NiFi orchestre chaque flux avec une chaîne de 6 processeurs : GetFile → ValidateRecord → RouteOnAttribute → TransformRecord → PutHDFS → LogMessage. Chaque FlowFile est suivi avec attributs UUID, taille, horodatage. La provenance complète est exportée dans reports/nifi_provenance.json.

Phase 04 — Talend ETL (Transformation) ✔ 7.1s — 136 358 × 47 cols

Le pipeline Talend réalise : nettoyage des types, conversion des IDs numériques (42786.0 → "42786"), mapping ESPECE_FR (W→Blé tendre, O→Colza, S→Tournesol…), jointures en cascade (Résultats ← Essai ← Parcelle ← Matériel ← Qualifications), puis construction de la table de faits étoile de 136 358 lignes × 47 colonnes.

Phase 05 — Apache HBase (NoSQL) ✔ 57.7s — 72 116 rows

3 tables HBase avec familles de colonnes :
• experiments : CF info, geo, quality, meta — row key : YEAR#EXP_ID
• results : CF measurement, metadata, meta — row key : EXP#TRIAL#ENTRY#TRAIT
• materials : CF identity, genetics, taxonomy, meta — row key : MAT_ID

Phase 06 — Apache Kafka (Streaming) ✔ 34.5s — 535 messages

4 topics Kafka simulés :
• experimental-results (3 partitions) : 500 nouveaux résultats produits et consommés
• quality-alerts (1 partition) : 15 alertes outliers détectées automatiquement
• geo-stream (2 partitions) : 20 événements NDVI/météo drones simulés
Taux de consommation : 100% (535 produits = 535 consommés)

Phase 08 — Apache Spark (Calcul distribué) ✔ 40.4s — PySpark 3.5.5

SparkSession en mode local[*] utilisant tous les cœurs CPU. Analyses :
• 38 combinaisons espèce×trait avec avg/std/min/max
• Top 30 matériels génétiques par rendement YD15QH
• Corrélation YD15QH × %MOIS = 0.2464 (corrélation faible positive)
• Audit qualité : REGION null à 81% (essais sans localisation précise)

Choix Technologiques & Justifications

Pourquoi chaque technologie a été sélectionnée

🐘

Hadoop / HDFS

Stockage distribué

Système de fichiers distribué tolérant aux pannes. Les données Parquet sont organisées en 3 couches : raw/, transformed/, enriched/ — reproduisant exactement la zone d'atterrissage HDFS d'un cluster Cloudera/MapR/HortonWorks en production.

💡 Pourquoi ? Standard de facto pour le stockage Big Data. Parquet/Snappy offre une compression ~70% vs CSV et des lectures colonnar ultra-rapides pour les analyses analytiques.

Apache Sqoop

Ingestion batch

Outil d'import/export de données entre SGBDR (MySQL, Oracle, PostgreSQL) et HDFS. Simule l'import depuis la base de données source CRISP vers le Data Lake. Support natif du format Parquet et de la parallélisation MapReduce.

💡 Pourquoi ? Sqoop est LA solution standard pour migrer les données relationnelles vers Hadoop. Bien plus fiable que les exports CSV manuels car il gère les types, la pagination et les reprises sur erreur.
6jobs réussis

Apache NiFi

Orchestration flux

Plateforme d'orchestration de flux de données avec interface visuelle. Chaque processeur (GetFile, ValidateRecord, RouteOnAttribute…) est indépendant et chain-able. La provenance complète de chaque FlowFile est tracée.

💡 Pourquoi ? NiFi offre une observabilité totale sur les flux de données — crucial dans un contexte réglementaire semencier (traçabilité variétale). Il complète Talend en gérant l'ingestion en temps quasi-réel.
6processors

Talend ETL

Transformation

Suite ETL enterprise pour la construction des pipelines de transformation. Gère le nettoyage des données, les jointures multi-sources, le mapping des référentiels et la construction du modèle en étoile (Kimball). Très utilisé chez les grands comptes agricoles.

💡 Pourquoi ? Talend est standard dans les DSI agricoles françaises et certifié MapR/Cloudera. Son approche visuelle permet aux équipes non-développeurs de maintenir les jobs ETL sans compétences de code.

Apache HBase

NoSQL Column-Family

Base de données NoSQL distribuée de type column-family, construite sur HDFS. Accès par row key en O(1). Utilisée ici pour stocker les expériences (2 116 rows), les résultats (50 000 rows) et les matériels (20 000 rows) avec des familles de colonnes métier.

💡 Pourquoi ? Pour les accès directs par identifiant d'expérience (dashboard en temps réel, API REST). Les SGBDR ne peuvent pas tenir la charge quand on requête 136K résultats par ID en parallèle depuis 300 utilisateurs.

Apache Kafka

Streaming temps réel

Bus de messages distribué orienté log avec rétention configurable. 4 topics : experimental-results (500 msg), quality-alerts (15 alertes outliers), geo-stream (20 événements NDVI/météo drones), material-updates. Producer/Consumer pattern avec partitionnement par clé.

💡 Pourquoi ? Les essais culturaux se déroulent en continu sur le terrain. Kafka permet d'alerter les équipes en temps réel quand un résultat anormal est détecté (outlier ±3σ), sans attendre le batch quotidien.

Apache Hive

Entrepôt analytique

Data Warehouse SQL sur Hadoop. Exécute du HiveQL sur les fichiers Parquet via DuckDB (équivalent fonctionnel HiveServer2/JDBC). 5 requêtes analytiques : rendement moyen espèce×année, top matériels, analyse régionale, tendance temporelle avec LAG(), taux de complétion.

💡 Pourquoi ? Les analystes métier maîtrisent le SQL. Hive leur permet d'interroger 136K résultats sans passer par les équipes Big Data. Les tables externes Parquet évitent toute duplication de données.

Calcul distribué

💡 Pourquoi ? Quand les volumes de données passeront à 10M+ de mesures (5 ans de données sur toutes les divisions), seul Spark peut traiter en temps acceptable. L'API DataFrame est identique localement et en cluster.

Moteur SQL ad-hoc sur fichiers (Parquet, CSV, JSON) sans définir de schéma préalable. SQL exploratoire via dfs.workspace permettant de joindre des fichiers de formats différents. 6 requêtes : schema discovery, cross-file join, outliers, TOP-N par région, métadonnées Parquet.

💡 Pourquoi ? Les data scientists ont besoin d'explorer rapidement de nouvelles sources sans attendre qu'un ETL soit développé. Drill permet des POCs analytiques en minutes sur n'importe quel fichier du Data Lake.

Exemples de Code

Extraits représentatifs des implémentations clés

Apache Drill — SQL ad-hoc cross-fichiers (sans ETL préalable)

-- Apache Drill — jointure de 2 fichiers Parquet indépendants -- Aucun schéma prédéfini — découverte automatique SELECT e.LK_EXPERIMENT_NAME, r.TRAIT, COUNT(*) AS nb_mesures FROM dfs.raw.`essai.parquet` e JOIN dfs.raw.`resultats.parquet` r ON CAST(e.EXPERIMENT_ID AS VARCHAR) = r.LK_EXPERIMENT_EXPERIMENT_ID GROUP BY e.LK_EXPERIMENT_NAME, r.TRAIT HAVING nb_mesures > 10 ORDER BY nb_mesures DESC LIMIT 15;

Apache Spark — Window function + corrélation (PySpark DataFrame API)

from pyspark.sql import SparkSession from pyspark.sql.functions import avg, count, col, round as spark_round spark = SparkSession.builder \ .appName("Semences_RD") \ .master("local[*]") \ .getOrCreate() df = spark.read.parquet("data/enriched/fact_table.parquet") # Top matériels par rendement — YD15QH best = df.filter( (col("TRAIT") == "YD15QH") & col("RESULT_NUM").isNotNull() ).groupBy("MAIN_NAME", "ESPECE_FR") \ .agg(count("*").alias("nb_obs"), spark_round(avg("RESULT_NUM"), 3).alias("rendement_moyen")) \ .filter(col("nb_obs") >= 3) \ .orderBy(col("rendement_moyen").desc()) \ .limit(30) # Corrélation YD × humidité corr = joined.stat.corr("yd", "humidity") # → 0.2464

Apache Kafka — Producer / Consumer pattern

# KafkaTopic avec partitionnement par clé class KafkaTopic: def produce(self, key: str, value: dict) -> int: partition = abs(hash(key)) % self.nb_partitions msg = { "topic": self.name, "partition": partition, "offset": self.offsets[partition], "key": key, "value": value, "timestamp": datetime.now().isoformat() } self.partitions[partition].put(msg) # O(1) self.offsets[partition] += 1 return partition # Production de 500 nouveaux résultats d'essais for _, row in fact.sample(500).iterrows(): key = f"{row['LK_EXPERIMENT_EXPERIMENT_ID']}_{row['TRAIT']}" topic.produce(key, {"result": float(row["RESULT_NUM"]), "year": int(row["YEAR"]), "event_type": "NEW_RESULT"})
